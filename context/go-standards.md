# Coding Standards

## Important

Never edit manually `go.mod` and `go.sum` file in each app. Run `TASK=tidy APP=<app> npm run task` to fix dependency.

### Executors

- `build`: Build a Go project
- `lint`: Format and lint a Go project
- `serve`: Run a Go application
- `test`: Run tests of a Go project
- `tidy`: Ensures go.mod file matches a project source code


## Go

- Use Go 1.22+
- No unused imports or variables
- Keep functions under 50 lines when possible
- No global state — inject all dependencies via constructors

## Architecture

ShotgunSMS follows a strict **layered architecture** — Handler → Service → Repository.

- **Handler** — parses request, validates input, calls service, writes response
- **Service** — owns all business logic
- **Repository** — database access only, no business logic

Each layer depends on the layer below via **interfaces**, never concrete types.

```go
type MessageService interface {
    Send(ctx context.Context, input SendMessageInput) (*domain.Message, error)
}
```

> The `consumer` and `worker` apps do not have HTTP handlers. They follow Service → Repository only.

## HTTP

- Use Go standard library `net/http` only — no third-party routers (no Gin, Echo, Chi)
- Go 1.22+ native routing supports method + path matching out of the box

```go
mux := http.NewServeMux()
mux.HandleFunc("POST /api/v1/fire", h.Fire)
```

- Always version routes under `/api/v1/`
- Use middleware chaining for auth and logging
- Never write raw response logic in handlers — always use `pkg/response` helpers

## Naming

- Files: `snake_case.go`
- Packages: short, lowercase, no underscores (`handler`, `service`, `repo`)
- Types and interfaces: `PascalCase`
- Functions and methods: `camelCase`
- Constants: `SCREAMING_SNAKE_CASE`
- Interface names describe behavior — `MessageRepository`, not `IMessage` or `MessageRepo`

## Database

- Use **GORM** for all database access
- Use `UUID` primary keys — generated by PostgreSQL (`gen_random_uuid()`), not the backend
- **Never use `gorm.Model`** — define models manually without `deleted_at`
- All models must define only: `ID`, `CreatedAt`, `UpdatedAt`, and domain-specific fields

```go
type Message struct {
    ID         uuid.UUID `gorm:"type:uuid;primaryKey"`
    To         string    `gorm:"type:varchar;not null"`
    Body       string    `gorm:"type:text;not null"`
    Status     string    `gorm:"type:varchar;not null;default:'queued'"`
    RetryCount int16     `gorm:"type:smallint;not null;default:0"`
    CreatedAt  time.Time
    UpdatedAt  time.Time
}
```

- Status transitions (`queued` → `sent` / `failed` → `exhausted`) are always done by the service layer, never the handler or repository

## Migrations

- All schema changes go through **Goose** migration files — never modify the DB directly
- Migration files live in `apps/migration/transactions/`
- Use SQL format with `-- +goose Up` and `-- +goose Down` directives
- File naming: `00001_create_messages.sql`, `00002_create_settings.sql`, etc.
- Run migrations manually before starting any app for the first time or after any schema change:

```bash
nx run migration
```

## GSM Module Pool

The module pool lives exclusively in the `consumer` app. No other app touches hardware.

- Each module has its own goroutine and serial connection
- Pool uses **round-robin** selection — always starts from `lastUsedIndex + 1`
- Module state is tracked **in-memory** — never query hardware per message send
- A **background health-check goroutine** (separate from message processing) runs every ~30s

```go
type ModuleStatus string

const (
    StatusIdle    ModuleStatus = "idle"
    StatusBusy    ModuleStatus = "busy"
    StatusError   ModuleStatus = "error"
    StatusOffline ModuleStatus = "offline"
)

type Module struct {
    Port     string
    Status   ModuleStatus
    LastUsed time.Time
    mu       sync.Mutex
}
```

- Use `sync.Mutex` on each module to prevent race conditions
- Hardware errors must update the module's in-memory status immediately
- Log all AT command interactions for debugging

## Error Handling

- Always handle errors explicitly — never ignore them
- Wrap errors with context using `fmt.Errorf`

```go
if err := s.repo.Create(ctx, &msg); err != nil {
    return fmt.Errorf("create message: %w", err)
}
```

- Define shared error types in `pkg/apperror`

```go
var (
    ErrNotFound     = errors.New("not found")
    ErrUnauthorized = errors.New("unauthorized")
)
```

- Map errors to HTTP status codes in the **handler only** — never in service or repository

## Context

- Always pass `context.Context` as the **first argument** to service and repository functions
- Use context for request-scoped values and cancellations
- Never store context in a struct

## Dependency Injection

- Use constructor functions — never global variables

```go
func NewMessageService(repo MessageRepository, mq mq.Publisher, db *gorm.DB) MessageService {
    return &messageService{repo: repo, mq: mq, db: db}
}
```

## Configuration

- All configuration is loaded from ENV variables — no hardcoded values
- Use `github.com/rodentskiedev/go-libraries/lib/env` to read ENV — never use `os.Getenv` directly
- The second argument to `env.GetEnv` is the fallback value

```go
import "github.com/rodentskiedev/go-libraries/lib/env"

host := env.GetEnv("HOST", "localhost")
port := env.GetEnv("PORT", "8080")
```

- Define a `Config` struct per app and populate via `env.GetEnv` on startup

```go
type Config struct {
    DatabaseURL           string
    RabbitMQURL           string
    GSMPorts              []string
    WorkerPollInterval    time.Duration
    WorkerRetryWindowDays int
}

func LoadConfig() Config {
    return Config{
        DatabaseURL:           env.GetEnv("DATABASE_URL", ""),
        RabbitMQURL:           env.GetEnv("RABBITMQ_URL", ""),
        WorkerPollInterval:    env.GetEnv("WORKER_POLL_INTERVAL", "30s"),
        WorkerRetryWindowDays: env.GetEnv("WORKER_RETRY_WINDOW_DAYS", "5"),
    }
}
```

## Security

- Validate and sanitize all inputs before passing to the service layer
- API authentication uses `X-API-Key` header — checked in middleware
- Never log message content (PII — phone numbers, SMS body)

## Testing

- Use **table-driven tests** with `t.Parallel()`
- Mock all interfaces — no real database in unit tests
- Integration tests live in `test/` and may use a real PostgreSQL instance
- Run tests:

```bash
go test ./... -cover
```

- Test files live next to source: `service_test.go` beside `service.go`

### When to write a test

Use judgment — not every function needs a test. Write a test when:

- The function contains **business logic** (e.g. retry limit checks, status transitions, round-robin selection)
- The function can **fail in non-obvious ways** (e.g. all modules busy, retry window edge cases)
- The function is a **service method** — these almost always warrant tests
- The function involves **input validation or transformation**

Skip the test when:

- The function is a **simple passthrough** (e.g. a repository method that just calls GORM with no logic)
- The function is **trivially correct** and has no meaningful branches
- The function is a **constructor** that only assigns fields

## Code Quality

- No commented-out code unless explicitly noted
- No unused imports or variables
- Export only what is necessary — keep internals private
- No `any` types — use proper types or `interface{}` with a clear comment explaining why
- Prefer early returns over nested conditionals

```go
// good
if err != nil {
    return fmt.Errorf("send message: %w", err)
}

// avoid
if err == nil {
    // happy path deeply nested...
}
```

## Logging

Use `github.com/rodentskiedev/go-libraries/lib/logger` for all logging. Never use the standard `log` package.

```go
import (
    "github.com/rodentskiedev/go-libraries/lib/logger"
    "go.uber.org/zap"
)

log := logger.New()
defer log.Sync() //nolint:errcheck

log.Info("message queued", zap.String("id", msg.ID.String()))
log.Fatal("fatal error", zap.Error(err))
```

- `logger.New()` returns a `*zap.Logger` — production logger in all envs, no-op when `ENV=test`
- Always `defer log.Sync()` after creating the logger
- Pass structured fields (`zap.Error`, `zap.String`, etc.) — never use format strings
- **Never log phone numbers or message body** — treat them as PII
