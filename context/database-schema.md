## Database Schema

PostgreSQL, managed via **Prisma ORM 7** (`prisma migrate`). UUID primary keys generated by PostgreSQL (`gen_random_uuid()`) so triggers and raw SQL inserts get IDs too.

Areas:

1. **Access control** — employees, users, roles, role permissions
2. **Medicine inventory** — medicines (catalog) + batches (stock, FIFO)
3. **Inventory movement** — transactions + per-batch entries (the only way stock changes)
4. **Notifications** — daily expiry digest (in-app + SMS), read state, SMS outbox for the Pi worker
5. **Settings** — single-row config
6. **Audit** — trigger-written log of inventory movement

---

## Entity overview

```
employees 1 ── 0..1 users N ── 1 roles 1 ── N role_permissions
    │                  │
    │                  ├── N inventory_transactions 1 ── N inventory_entries N ── 1 medicine_batches
    │                  └── N notification_reads N ── 1 notifications (1 per day)       │
    │                                                      │                           │
    │                                                      └── N notification_items N ─┤
    │                                                                                  │
    └── N sms_messages N ── 1 notifications          medicine_batches N ── 1 medicines
              │
              └── N sms_attempts

settings (single row)        audit_logs (append-only, trigger-written)
```

## Access Control (RBAC)

- A user has **exactly one role** (`users.role_id`).
- A role has a list of **permission strings** (`role_permissions.permission`).
- The default is deny, and there are **no explicit deny rules**. A permission is either granted or it isn't.
- Wildcards: `resource:*` matches every action on that resource, and `*` matches everything (admin).

The valid permission strings are a constant in code (`src/lib/permissions.ts`). Writes to `role_permissions` are validated against that list with Zod, so a typo can't grant nothing silently.

| Permission           | Meaning                                        |
| -------------------- | ---------------------------------------------- |
| `medicine:read`      | view medicines, batches, expiry status         |
| `medicine:write`     | create/edit medicines and batches              |
| `inventory:read`     | view transactions/entries                      |
| `inventory:write`    | record receive / dispense / adjustment         |
| `notification:read`  | view in-app notifications                      |
| `employee:manage`    | manage employees, SMS recipients               |
| `user:manage`        | manage user accounts and roles                 |
| `settings:manage`    | edit settings                                  |
| `audit:read`         | view audit logs                                |

Seeded roles (`is_system = true`): `admin` → `*`, `staff` → `medicine:*`, `inventory:*`, `notification:read`, `collaborator` → `medicine:read`, `inventory:read`, `notification:read`.

### Employees ↔ users

- An **employee** is a person and a **user** is a login. Every user belongs to exactly one employee (`users.employee_id` is unique). An employee may have no login, for example a pharmacist who only receives SMS.
- `receives_sms_alerts = true` requires `contact_number` (DB `CHECK` plus Zod).
- `contact_number` is stored normalized to E.164 so the worker can dial it as-is.
- Login uses `users.username`, and `employees.email` is contact info only. Keeping credentials on `users` means editing a person's profile never touches auth.

## Medicine Inventory & FIFO

- **`medicines`** is the catalog item.
- **`medicine_batches`** is the physical stock. Each batch has its own `batch_number`, `barcode`, `expiration_date`, `received_at`, and `quantity`.
- Total stock for a medicine is `SUM(medicine_batches.quantity)`. It is computed, never stored.
- Expiry status is computed **per batch** at read time and never stored:
  - `expiration_date < today` → **Expired**
  - `expiration_date - today <= settings.near_expiry_threshold_days` → **Near Expiry**
  - otherwise → **Safe**
  - "today" is in `settings.timezone`.

### Barcodes

Both medicines and batches get an app-generated barcode, each with its own prefix: `MED-…` for medicines and `BAT-…` for batches. The scanner routes on the prefix, so the two kinds can never collide.

| Scanned          | Resolves to  | Used for                                                          |
| ---------------- | ------------ | ----------------------------------------------------------------- |
| Medicine barcode | the medicine | lookup and dispensing (FIFO picks the batches)                    |
| Batch barcode    | one batch    | receiving more of that batch, count correction, damaged/lost, expired disposal |

### FIFO allocation

Stock goes out **first-expired, first-out** (FEFO). That is the standard for medicines and is the same as FIFO whenever the earlier stock also expires earlier. Ties fall back to arrival order: `ORDER BY expiration_date, received_at, id`.

To dispense N units of a medicine, the app does the following in one interactive `prisma.$transaction`:

1. `SELECT set_config('app.actor_id', <userId>, true)` sets the audit actor.
2. Lock the medicine's usable batches:
   ```sql
   SELECT id, quantity FROM medicine_batches
   WHERE medicine_id = $1 AND quantity > 0 AND expiration_date >= $today
   ORDER BY expiration_date, received_at, id
   FOR UPDATE;
   ```
3. Walk the batches and take `min(remaining, batch.quantity)` from each until N is covered. If the batches run out first, abort with an "insufficient stock" error.
4. Insert one `inventory_transactions` row (`OUT`, `DISPENSED`, quantity N) and one `inventory_entries` row per batch touched.
5. The quantity-sync trigger decrements each batch.

Expired batches are excluded from `DISPENSED`. They leave stock only through an explicit `EXPIRED_DISPOSAL` transaction.

### Inventory transactions (all stock changes)

**Every stock change is an inventory transaction**:

| Action             | direction | reason             | Entries                                                 |
| ------------------ | --------- | ------------------ | ------------------------------------------------------- |
| Receive stock      | IN        | `RECEIVED`         | 1 entry on a new batch, or on an existing batch with the same number + expiry |
| Dispense           | OUT       | `DISPENSED`        | N entries, FIFO-allocated                               |
| Count correction   | IN / OUT  | `COUNT_ADJUSTMENT` | 1 entry on the specified batch                          |
| Damaged / lost     | OUT       | `DAMAGED` / `LOST` | 1 entry on the specified batch                          |
| Expired disposal   | OUT       | `EXPIRED_DISPOSAL` | 1 entry per expired batch                               |

Transactions and entries are **immutable**: they have no `updated_at` or `deleted_at`, and a trigger rejects UPDATE/DELETE. To fix a mistake, post an offsetting transaction.

## Notifications & SMS

Notifications are a **daily digest**. Once a day, one `notifications` row lists every batch that is near expiry or expired and still in stock. The same digest is shown in-app and texted as **one SMS per recipient per day**.

A batch keeps appearing in every daily digest until it is **disposed**, meaning its quantity reaches 0, usually through an `EXPIRED_DISPOSAL` transaction.

### Daily generation (server)

`generateDailyNotification()` is idempotent:

1. Compute `today` in `settings.timezone`. If the local time is before `settings.daily_notification_time`, stop.
2. `INSERT INTO notifications (notification_date) VALUES (today) ON CONFLICT DO NOTHING`. If no row was inserted, today's digest already exists, so stop. This unique date makes concurrent calls safe.
3. Insert `notification_items` for every batch where `quantity > 0 AND expiration_date - today <= near_expiry_threshold_days`. Snapshot `status`, `quantity`, `expiration_date` and `days_to_expiry`, then set `expired_count` / `near_expiry_count`.
4. If there are no items, stop. The empty row records that today ran, and the UI hides it.
5. Cancel any older `PENDING` `sms_messages`, since today's digest supersedes them and a stale list is never sent.
6. If `settings.sms_enabled`, insert one `sms_messages` row per active employee with `receives_sms_alerts = true`. The row snapshots `phone_number` and the rendered `body`.

It runs at the start of every worker poll and when the app loads notifications, so no separate cron is needed. The in-app digest still appears when the worker is offline.

In-app:

- The bell shows the latest digest and its items.
- Read state is per user in `notification_reads`. A digest is unread for a user while no row exists for that pair.
- Live batch status on inventory screens is still computed at read time, so it is always current between digests.

### SMS body

The body is rendered from `settings.sms_template`:

- Placeholders: `{facility}`, `{date}`, `{expired}`, `{near_expiry}`, `{items}`.
- `{items}` lists up to `settings.sms_max_items` lines, expired first and then by soonest expiry, e.g. `Paracetamol 500mg B#A123 exp 2026-11-02 (3d)`.
- If there are more items, it ends with `+N more, check InventraMed`.

### SMS delivery tracking (worker)

`sms_messages` is an **outbox**, and `UNIQUE (notification_id, employee_id)` means each employee is texted at most once per day. Each row answers: was today's digest delivered to this employee, when, and after how many tries? `sms_attempts` logs every individual try for monitoring and debugging (modem errors, signal issues).

```
PENDING ──claim──► SENDING ──result ok──────────────────► SENT
   ▲                  │
   │                  ├─result fail, attempts < max ──────► PENDING (next_attempt_at = now + retry delay)
   │                  ├─result fail, attempts = max ──────► FAILED
   └──claim timeout───┘   (worker died mid-send)

PENDING ──recipient opted out / superseded by a newer digest──► CANCELLED
```

Worker API (Next.js route handlers, bearer token `WORKER_API_TOKEN` from env):

1. **`POST /api/worker/sms/claim`** updates `settings.worker_last_seen_at`, runs `generateDailyNotification()`, then atomically claims up to `sms_batch_size` messages:
   ```sql
   UPDATE sms_messages
      SET status = 'SENDING', claimed_at = now(), attempts = attempts + 1, updated_at = now()
    WHERE id IN (
      SELECT id FROM sms_messages
       WHERE (status = 'PENDING' AND next_attempt_at <= now())
          OR (status = 'SENDING' AND claimed_at < now() - make_interval(mins => $timeout))
       ORDER BY created_at
       LIMIT $batchSize
       FOR UPDATE SKIP LOCKED)
   RETURNING id, phone_number, body, attempts;
   ```
2. **`POST /api/worker/sms/:id/result`** takes `{ success, error?, modemResponse? }` and, in one transaction:
   - inserts an `sms_attempts` row
   - sets status to `SENT` + `sent_at`, or back to `PENDING` with a backoff, or to `FAILED` once `attempts >= sms_max_attempts`

The worker reports each result **right after each send**, not in a batch, which keeps the window for duplicates small. Delivery is at-least-once: if the Pi dies after the modem sends but before it reports, the claim timeout requeues that message and it may go out twice. That is acceptable for alerts.

Cancellation: when an employee turns off `receives_sms_alerts` or is deactivated, their `PENDING` messages are set to `CANCELLED`. A new day's digest also cancels any older `PENDING` messages (step 5 above).

## Settings

Single row (`id = 1`, enforced by `CHECK`), seeded by the first migration. Notable fields:

- `timezone` is `Asia/Manila` (UTC+8) and defines "today" for expiry math and the daily digest.
- `near_expiry_threshold_days` sets the Safe → Near Expiry boundary.
- `daily_notification_time` is the local time the daily digest is generated and SMS is queued.
- `sms_*` controls the worker: on/off, retries, claim lease, batch size, items per SMS, and the message template.
- `worker_last_seen_at` is a heartbeat, so the UI can warn when the Pi worker is offline.

## Audit Trail

`audit_logs` is append-only. Its triggers are attached **only to inventory movement**:

| Table                    | Events                     | Why                                                        |
| ------------------------ | -------------------------- | ---------------------------------------------------------- |
| `inventory_transactions` | INSERT                     | who moved stock, why, how much                             |
| `inventory_entries`      | INSERT                     | which batches were touched                                 |
| `medicine_batches`       | INSERT / UPDATE / DELETE   | before/after `quantity`, plus manual edits to expiry/batch no. |

`actor_id` is read from `current_setting('app.actor_id', true)`. Every inventory write path must set it at the start of its `$transaction` (step 1 of FIFO allocation above). Put this in one helper, `withActor(userId, fn)`, so no caller can forget it. Without it, `actor_id` ends up NULL.

### Quantity sync

```sql
CREATE FUNCTION apply_inventory_entry() RETURNS trigger AS $$
DECLARE
  tx inventory_transactions%ROWTYPE;
BEGIN
  SELECT * INTO tx FROM inventory_transactions WHERE id = NEW.transaction_id;

  UPDATE medicine_batches
     SET quantity = quantity + CASE WHEN tx.direction = 'IN' THEN NEW.quantity ELSE -NEW.quantity END,
         updated_at = now()
   WHERE id = NEW.batch_id AND medicine_id = tx.medicine_id;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'batch % does not belong to medicine %', NEW.batch_id, tx.medicine_id;
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER inventory_entries_apply
  AFTER INSERT ON inventory_entries
  FOR EACH ROW EXECUTE FUNCTION apply_inventory_entry();
```

If a deduction would push a batch below zero, `medicine_batches_quantity_nonneg` fails and the whole transaction rolls back.

### Audit

```sql
CREATE FUNCTION write_audit_log() RETURNS trigger AS $$
DECLARE
  actor uuid := NULLIF(current_setting('app.actor_id', true), '')::uuid;
BEGIN
  INSERT INTO audit_logs (entity_type, entity_id, action, changes, actor_id)
  VALUES (
    TG_TABLE_NAME,
    COALESCE(NEW.id, OLD.id),
    CASE TG_OP WHEN 'INSERT' THEN 'created' WHEN 'UPDATE' THEN 'updated' ELSE 'deleted' END,
    jsonb_build_object(
      'before', CASE WHEN TG_OP = 'INSERT' THEN NULL ELSE to_jsonb(OLD) END,
      'after',  CASE WHEN TG_OP = 'DELETE' THEN NULL ELSE to_jsonb(NEW) END
    ),
    actor
  );
  RETURN COALESCE(NEW, OLD);
END $$ LANGUAGE plpgsql;

CREATE TRIGGER inventory_transactions_audit AFTER INSERT ON inventory_transactions
  FOR EACH ROW EXECUTE FUNCTION write_audit_log();
CREATE TRIGGER inventory_entries_audit AFTER INSERT ON inventory_entries
  FOR EACH ROW EXECUTE FUNCTION write_audit_log();
CREATE TRIGGER medicine_batches_audit AFTER INSERT OR UPDATE OR DELETE ON medicine_batches
  FOR EACH ROW EXECUTE FUNCTION write_audit_log();
```

`updated_at` is maintained by Prisma's `@updatedAt`. Triggers that update rows directly set `updated_at = now()` themselves, as `apply_inventory_entry` does.
