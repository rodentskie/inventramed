# History

- **Project scaffold** `Oct. 30, 2026` - setup project, context.
- **Database setup** `Oct. 31, 2026` - Prisma 7 + PostgreSQL in `apps/app` ([spec](features/01-database-setup.spec.md)).
  - Full schema with an initial migration that includes CHECK constraints, quantity-sync, immutability and audit triggers, and the settings row
  - Idempotent seed for the system roles (`admin`, `staff`, `collaborator`)
  - `src/lib/`: `prisma` client (pg adapter), `withActor`, `permissions` + unit tests
  - Nx `prisma:*` targets; `build`/`test`/`typecheck` generate the client first; real `typecheck` covering `prisma/`
  - Local DB via the root `compose.yml`
- **Authentication and Medicine API** `Nov. 5, 2026` - NextAuth login and REST routes for medicines and batches in `apps/app` ([spec](features/02-api-medicine.spec.md)).
  - `next-auth` v4 with the Credentials provider only, 8-hour JWT sessions, and `requirePermission`, which reads role and active status from the database on every request
  - Login attempt limit with a timed cooldown and a "try again after n minutes" response: new `users.failed_login_attempts` and `users.last_login_attempt_at` columns, plus `LOGIN_MAX_ATTEMPTS` and `LOGIN_COOLDOWN_MINUTES`
  - `/api/medicines` CRUD with soft delete, duplicate rejection and generated `MED-` barcodes; a medicine can't be deleted until its stock is 0
  - `/api/medicines/:id/batches` to receive stock, read and edit batches, with generated `BAT-` barcodes and computed expiry status; no batch delete
  - New audit trigger on `medicines`, and every medicine and batch write goes through `withActor`
- **Create Employee API** `Nov. 6, 2026` - REST routes to list roles and create employees with their logins in `apps/app` ([spec](features/03-employees.spec.md)).
  - `POST /api/employees` inserts the `employees` and `users` rows in one `prisma.$transaction`, because every employee must have an account
  - `GET /api/roles` returns role IDs for `roleId`; `roles` and `role_permissions` stay seeded and read-only
  - Both routes use `requirePermission` and the NextAuth session cookie, and only `admin` holds the required permissions today
  - Contact numbers must be Philippine mobile numbers (`+639XXXXXXXXX`), usernames are lowercase only, and passwords are bcrypt cost 12 hashes limited to 72 bytes
  - No migration and no audit logging for these tables
- **Employee Read, Update and Delete API** `Nov. 6, 2026` - Finishes employee CRUD in `apps/app` ([spec](features/04-employees-crud.spec.md)).
  - `GET /api/employees` with search and paging, `GET`, `PATCH` and `DELETE /api/employees/:id`, all requiring `employee:manage` and `user:manage`
  - `PATCH` edits both tables in one transaction, and `isActive` sets both active flags; passwords can't be changed here
  - Delete is a soft delete with no restore, and deleted emails and usernames stay reserved
  - Turning alerts off, deactivating or deleting cancels `PENDING` SMS messages
  - Callers can't change their own role, deactivate themselves or delete themselves, and an advisory lock guards against removing the last active admin
- **Inventory Movement API** `Nov. 6, 2026` - REST routes that move stock out of and back into batches and read the ledger in `apps/app` ([spec](features/05-inventory-movement.spec.md)).
  - `POST /api/medicines/:id/dispense` allocates first-expired, first-out across batches and never touches expired ones
  - `POST /api/medicines/:id/batches/:batchId/movements` records damaged, lost, returned and count-corrected stock, with the count difference worked out under lock
  - `POST /api/medicines/:id/expired-disposal` removes the whole of every expired batch, or only those in `batchIds`
  - `GET /api/inventory/transactions` with filters and paging, and `GET /api/inventory/transactions/:id`; deleted medicines keep their history
  - Every movement takes the `lockActiveMedicine` lock in one `withActor` transaction, and one helper writes the transaction and entries, so the quantity always equals the sum of its entries
  - No migration; adds `INSUFFICIENT_STOCK`, `NO_EXPIRED_STOCK` and `BATCH_NOT_EXPIRED`, and the `RETURNED` row in `database-schema.md`
- **Settings API** `Nov. 6, 2026` - REST routes to read and update the single `settings` row in `apps/app` ([spec](features/06-settings.spec.md)).
  - `GET` and `PATCH /api/settings`, both requiring `settings:manage`; no create or delete, so the row stays at `id = 1`
  - `PATCH` sets `updated_by` to the caller, uses a strict schema, and can't write `worker_last_seen_at`
  - Zod enforces limits on every number, including the columns with no database check, plus `HH:mm` times, IANA timezones (UTC offsets are rejected) and known SMS template placeholders
  - No migration and no audit logging; adds `jest` and `@types/jest` to `apps/app` dev dependencies
- **Daily Digest and In-App Notifications** `Nov. 7, 2026` - Generates the daily expiry digest and adds REST routes to read it in `apps/app` ([spec](features/07-notifications.spec.md)).
  - `generateDailyNotification()` runs at the start of `GET /api/notifications` and creates at most one digest per day, in one `prisma.$transaction`, so a failure leaves no partial digest
  - Queues one `sms_messages` row per active recipient, and cancels older `PENDING` and timed-out `SENDING` messages even on a day with no items
  - `GET /api/notifications` with paging and `unreadCount`, `GET /api/notifications/:id`, and `POST /api/notifications/:id/read`, all requiring `notification:read`; empty digests are hidden and return `404`
  - Read state is per user. Marking as read uses `createMany` with `skipDuplicates` instead of the spec's upsert, because Prisma's `upsert` with an empty `update` failed with `P2002` on concurrent calls
  - No migration; updates the generation steps in `database-schema.md`
- **SMS Worker API** `Nov. 7, 2026` - Adds the two bearer-token endpoints the Raspberry Pi worker uses to claim queued SMS and report results in `apps/app` ([spec](features/08-sms-worker-api.spec.md)).
  - `POST /api/worker/sms/claim` runs `generateDailyNotification()`, sets `FAILED` on timed-out messages with no attempts left, then claims up to `sms_batch_size` messages from the latest digest using a CTE with `FOR UPDATE SKIP LOCKED`. It also returns `pollIntervalSecs`
  - `POST /api/worker/sms/:id/result` takes the `attempt` from the claim and records the result in one transaction. A repeated or late result returns `200` with `applied: false`
  - Auth compares SHA-256 hashes of `WORKER_API_TOKEN` with `timingSafeEqual`, and rejects every call if the token isn't set
  - Both endpoints update `worker_last_seen_at` with raw SQL, so `settings.updated_at` still describes the last admin edit. This includes calls that then fail validation
  - No migration; adds `WORKER_API_TOKEN` to `.env.example` and updates the worker flow in `database-schema.md`
- **Audit Log API** `Nov. 7, 2026` - Adds a read-only REST route to list `audit_logs` in `apps/app` ([spec](features/09-audit-logs.spec.md)).
  - `GET /api/audit-logs` requires `audit:read`, and filters by `entityType`, `entityId`, `action`, `actorId`, `from` (inclusive) and `to` (exclusive), with paging, sorted by `createdAt` descending, then `id`
  - `from` and `to` need an offset, so the caller sets the timezone. A `+` in the query string must be encoded as `%2B`
  - `actor_id` has no foreign key, so actors come from one `user.findMany` over the page's distinct IDs, and `actor` is `null` for a `NULL` `actor_id`
  - `changes` is returned as stored, and there is no detail endpoint
  - No migration and no new dependencies
- **Login UI** `Nov. 7, 2026` - Adds the first real screen in `apps/app`: a Chakra login page on top of the existing NextAuth credentials provider ([spec](features/10-login.spec.md)).

  - Dark mode is the default, with a light mode toggle. Adds the `password-input` and `toaster` snippets, with `rootProps` retyped in `password-input` to fix a TS2590 error
  - Adds a `build` target to `libs/components`, and `typecheck` now depends on `^build`, because the app's project reference needs the lib's declarations in `dist`
  - No migration and no new dependencies
